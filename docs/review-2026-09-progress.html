1. Executive summary

Llama AIO is a well-scoped, genuinely useful project: it installs and runs llama-server, exposes local models to Copilot Chat, and gives a resource estimate before loading. The core library is solid and well tested (429 passing tests, clean lint). The weaknesses are concentrated in three places: synchronous I/O and process spawning on the UI thread, a 4,500-line inline webview that re-implements core logic, and a handful of lifecycle/correctness bugs (process killing, tool-call streaming, memory accounting) that users will hit in ordinary sessions.

2. Methodology

  • Full read of packages/vscode/src (extension, settings webview, model picker, HF flow, chat provider) and targeted reads of packages/core/src and packages/tui/src — ~29.5 k lines of TypeScript.
  • Four parallel deep-dives (core process/installer, chat provider & perf stats, memory/model/HF, TUI) with every High/Critical claim re-verified against the source at the quoted file:line.
  • Build check: npm install --ignore-scripts, npm run lint (clean), npm test (429 pass, 0 fail). Node 22 in the review environment; the TUI declares node >= 26.4 with --experimental-ffi, so TUI findings are from code reading only.
  • Screenshots in media/ were used as the reference for the current GUI.
  • Severity: Critical broken in the normal path · High data loss, wrong result, or user-visible stall · Medium incorrect in realistic edge cases · Low cosmetic / hardening.

4. Performance bottlenecks

Almost all latency in the VS Code extension is self-inflicted: the core API is synchronous, and the extension calls it from event handlers on the extension-host thread. The chat provider adds a separate, much larger problem in Agent mode.

4.1 What happens when you click a model in the sidebar

webview postMessage→ config write (tmp+rename)→ pushState()→ isHttpReady() ×2 (HTTP)→ readGgufMetadata (sync, per-field readSync)→ listLocalModelEntries (walk ~25 roots, depth 8)→ getInstalledInfo (--version spawnSync)→ getUiBackendOptions → detectCudaHardware (sh -c, nvidia-smi 3 s)→ detectGpus (spawnSync --list-devices, 8 s timeout)→ estimateMemory (re-reads draft GGUF, rescans dir)→ findSiblingMtpDraft + mmprojFileSize→ postMessage state

Measured/expected cost per click: ~300 ms warm on a fast SSD with an NVIDIA GPU; 3–11 s when the GPU cache is cold, nvidia-smi is missing (waits for the 3 s timeout), or a model root is on a network/slow disk. During this time the whole extension host is blocked — other extensions stall too.

7. Architecture & maintainability notes

Strengths

  • Clear monorepo split; core is UI-agnostic and reused by both front-ends.
  • Atomic config writes with external-change detection; install swap with rollback.
  • 429 unit tests around the hard parts (GGUF parsing, estimate, args, HF parsing).
  • Pragmatic GPU detection with multiple fallbacks and a cache.

Risks

  • settingsView.ts: 4,569 lines, HTML/CSS/JS in one template string; no bundling, no type-checking, no tests for the webview logic.
  • Three estimators (core, webview liveMemoryEstimate, TUI) and three preset tables that already diverge.
  • Synchronous core API forces every consumer onto the UI thread.
  • Zero tests in packages/vscode and packages/tui.
  • No Output channel or structured logging in the extension; failures surface only as toasts.
  • Process lifecycle relies on a PID in a JSON file with no identity check and no inter-process lock. Done B-01 / B-03 / B-08 — identity check, launch lock, atomic write. Remaining: B-04 process-group kill on POSIX, B-55 TUI dispose.
Suggested structural change. Introduce a small state service in the extension (one poller, one cache, event emitter) that both the status bar and the webview subscribe to; move all computation to core async functions; bundle the webview as a TypeScript entry that imports display-only helpers from core. Most of the bug list in 3.4 and half of the performance list disappear as a side effect.
Architecture risks — what changed. Process identity and an inter-process launch lock now exist (B-01, B-03, B-08). Agent-mode buffering is gone (P-01). Downloads are a real manager (F-03). Remaining structural risks are unchanged: the ~4.7k-line inline webview and duplicate estimator (F-13 / B-48), synchronous core on the UI thread (F-04), and zero tests in vscode / tui (F-14).
