How the two fit algorithms decide what to load

llama.cpp’s --fit (default on) does dummy allocations against free device memory and rewrites -c, -ngl, --tensor-split, and --override-tensor. Llama AIO always passes --fit off and instead picks those knobs in TypeScript from a GGUF-based estimate, then launches with explicit flags.

TL;DR

They solve different jobs. llama.cpp fits at process start so a CLI user can omit -ngl and still not OOM. Llama AIO fits in the UI before start so the user can see bars, change context / KV types / speculative, and then start with those exact flags.

llama.cpp --fit

Maximize GPU fill, then cut until it fits

Start from “everything on GPU at trained context.” If that overflows, shrink context first (floor --fit-ctx, default 4096), then move tensors to RAM. MoE experts go to CPU before dense attention. Layers can overflow mid-layer onto the next GPU.

Budget: currently free VRAM − 1024 MiB per device. Accuracy comes from no_alloc dummy loads and the real memory breakdown (model + context + compute).

Llama AIO recommend

Keep a coding-agent context, then spill weights

Lock context at min(65536, model max). On two+ GPUs, try a tensor split that fully offloads. Only then raise --n-cpu-moe (MoE) or drop -ngl (dense). “Max context” is a separate preset that walks context steps.

Budget: total VRAM with 2 GiB headroom (one GPU) or 8% free per card (two+). Instant heuristic: file size, KV formula, ~400 MiB + batch overhead.

The context-first vs layers-first split is a product choice, not a bug. llama.cpp will happily drop a 128k window to 4096 to keep weights on GPU. A Copilot-style agent wants the opposite: keep ~64k, accept some CPU experts or a few RAM layers. Do not copy llama.cpp’s reduction order blindly.

Why Llama AIO always sends --fit off

llama.cpp treats -ngl, --tensor-split, --n-cpu-moe / tensor overrides, and an explicit --ctx-size as “user already decided.” If those are set, --fit either aborts (“n_gpu_layers already set”) or refuses to change the allocation. Llama AIO always writes those flags, so a live --fit pass cannot refine them — it only fights the UI.

Speculative drafts make it worse: sidecar MTP and DFlash need --fit off or the dummy probe mis-accounts the extra model. That is the same reason the settings help text says auto-fit “breaks DFlash / Gemma 4 MTP.”

Source: packages/core/src/serverArgs.ts (comment on --fit off); llama.cpp common_params_fit_impl throws if n_gpu_layers, tensor_split, or tensor_buft_overrides are already set.

Using total VRAM, not free, is correct for this UI. Recommendations run while a previous llama-server may still own the cards. llama.cpp’s free-memory budget is right at launch after the old process is gone. Subtracting live occupancy here would under-offload every reload.

Max-context preset (AIO only)

Separate from model-select recommend. Walks 262144, 196608, 163840, 131072, 98304, 65536, 49152, 32768, 24576, 16384, 8192 with KV forced to q8_0 / q4_0, and takes the first step whose estimate does not willSpill. llama.cpp instead linearly interpolates n_ctx between --fit-ctx and trained max using two dummy measurements.

Same hardware, different answers

GPT-OSS 120B mxfp4 · 1× 24 GB · want long chat

llama.cpp (unset -c): drop context toward 4096, keep almost all dense tensors on GPU, park most experts in RAM with -ot. High tok/s, short window.

Llama AIO (Coding agent): keep 64k, -ngl 99, raise --n-cpu-moe until ~2 GiB headroom. Window stays useful; more expert traffic on CPU.

Dense 32B Q4 · 2× 16 GB

llama.cpp: measure both cards, assign contiguous layer counts (later layers on GPU1 first), maybe overflow one FFN tensor. Context stays at trained max if the two cards hold it.

Llama AIO: try 50/50 … 70/30, pick the even-est peak. Full -ngl 99 if the heuristic says neither card spills. If not, proportional split then drop layers — it will not overflow a single layer across the PCIe link.

Keep doing this

  1. Leave --fit off while the UI owns -ngl / split / MoE / ctx. Turning it on without omitting those flags is a no-op or an abort.
  2. Budget against total VRAM for recommend-on-select. Live used belongs in the “free now” line, not the fit inequality — unless you can exclude this extension’s own server.
  3. Prefer 64k then spill weights for the default / Coding agent path. That is the right bias for Copilot Chat.
  4. Keep the cheap estimator in the live bars. Dummy-loading on every slider tick would freeze the webview.
  5. Split-across-GPUs before RAM on two cards is already the right order, and it matches what users expect from llama.cpp.
  6. Raise -ub only when fully GPU-bound. Partial offload is CPU-bound; a bigger physical batch just wastes VRAM.

Anything you could do better

Ranked by impact on real loads. None of these require copying llama.cpp’s context-first policy.

P1 Unify headroom to a fixed GiB, not 8% of a huge card

One GPU requires 2 GiB free vs total. Two GPUs require 8% free per card. On 2× 80 GB that is 6.4 GiB idle per GPU — llama.cpp would happily use all but 1 GiB. On 2× 12 GB, 8% is only ~1 GiB, looser than the single-GPU rule. Use the same rule everywhere: e.g. min(2048 MiB, 8% of total) or llama.cpp’s 1024 MiB, applied to total − estimate.

recommendSettings.ts VRAM_HEADROOM_BYTES vs memoryEstimate.ts usableFraction = 0.92 and dual fitsHeadroom using willSpill.

P1 Emit --override-tensor for MoE instead of only --n-cpu-moe

llama.cpp’s win on MoE is not the search — it is the representation. --n-cpu-moe N moves all experts of the first N layers to CPU. -ot blk\.\d+\.ffn_(up|down|gate)_(ch|)exps=CPU keeps every layer’s attention (and often the dense FFN) on GPU and only spills routed experts. For GPT-OSS / Qwen-MoE that is the difference between “24 GB is enough for dense + KV” and “we had to CPU-MoE 20 layers.” You already know moeExpertShare from the GGUF tensor scan; the next step is to generate the same regex llama.cpp uses when the estimate says dense-only fits.

P1 Optional ground-truth probe via llama-fit-params

Keep the heuristic for live bars. On model select (or a “Calibrate” button), run llama-fit-params with --fit-ctx 65536 (or the current target) and without -ngl, then parse the printed -c -ngl -ts -ot back into the form. That is the only way the estimate matches compute-graph scratch, FA vs not, and backend-specific allocators. Map llama.cpp’s context-first result back onto AIO policy: if it cut context below the agent target, restore 64k and convert the extra VRAM need into more CPU experts / fewer layers.

P2 Make the multi-GPU search capacity-aware and N-GPU

The share grid [0.50 … 0.70, 0.45 … 0.30] is a dual-GPU even-card heuristic. It does not know that GPU0 is 32 GB and GPU1 is 12 GB until full offload fails. Seed the first candidate with VRAM-proportional shares (what llama.cpp uses when -ts is empty), then search a small neighborhood around that. For 3+ cards, assign contiguous layer counts (back-to-front, like llama.cpp) rather than “main gets S%, everyone else splits the rest evenly.” Put compute + mmproj + draft on Main in the search (you already do in the bars) so Main is not over-filled with weights.

fitDualGpuFullOffload, tensorSplitForMainShare.

P2 Count parallel slots in KV

llama.cpp multiplies context by n_seq_max when KV is not unified. AIO’s estimate is for one sequence. If a user sets Max concurrent predictions > 1, the bars understate KV and recommend will over-commit. Multiply KV by slots unless --kv-unified is on (unified still grows, but not linearly with slots the same way).

P2 Replace max-context steps with a binary search (or interpolation)

Eleven coarse steps jump from 96k to 64k to 48k. The estimate is cheap — binary-search n_ctx between 8192 and model max (align to 256, like CUDA). Optionally expose the found value as “this is the largest that still leaves headroom” instead of snapping to the ladder.

Duplicated in settingsView.ts fittingContext and packages/tui/src/app.ts — one function in core would help.

P2 Stop double-counting baked-in MTP heads

estimateMtpFootprint adds fileSize × (nextn / nLayers) as extra GPU weights even though those tensors are already in the GGUF size used for the main load. llama.cpp’s extra-model path zeros mb.model when shares_model is set and only adds extra context/compute. Count MTP KV (and any extra compute) but not the heads twice, or the fitter will drop layers / raise CPU-MoE for a cost that is not real.

P3 Subtract other processes’ VRAM, not this server’s

You already read usedBytes. If you can tell compositor / browser / a second inference stack apart from the llama-server you are about to replace, subtract only the foreign used. That closes the gap with llama.cpp’s free-memory target without breaking reload.

P3 Dense partial-layer overflow on 24 GB

llama.cpp’s “one overflowing layer” exists because a single 70B layer can be several GB, so rounding to whole layers wastes a card. Worth it only if you start emitting -ot; not worth a second heuristic for -ngl alone.

P3 Do not copy regula falsi

llama.cpp interpolates layer counts because each probe is a dummy load (seconds). Your estimator is O(layers) arithmetic. Linear search of -ngl and n-cpu-moe is already the right algorithm.
